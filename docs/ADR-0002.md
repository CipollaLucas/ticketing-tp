# ADR-0002 — Dominio, consistencia y límites de servicios

Fecha: 2026-11-23. Estado: propuesta para revisión, issue #4.

## Contexto
La venta no debe duplicar un asiento ni exceder un cupo. El despliegue actual es una API con PostgreSQL. Separar inventario de órdenes obligaría a coordinar escrituras distribuidas antes de tener un flujo funcional.

## Decisión propuesta
Mantener límites lógicos y propiedad exclusiva de datos:

| Límite | Datos propios | Interacción |
|---|---|---|
| Identity | Usuarios, roles, sesiones | Autenticación y autorización síncronas en la API actual |
| Events | Evento, propietario, lugar, horarios y publicación | Lectura pública y edición autorizada; valida publicación con Ticketing |
| Ticketing | Zonas vendibles, asientos, cupos, precios, órdenes, tickets y devoluciones | Transacción PostgreSQL para toda venta/devolución |
| Notifications futuro | Entregas y reintentos | Consumidor asíncrono de eventos de dominio |

En Events el lugar describe el recinto; las zonas/asientos vendibles de un evento pertenecen a Ticketing. La configuración se congela al publicar. Cambios de fecha, precio, aforo o despublicación con ventas requieren una política y change posterior; inicialmente se rechazan (409). No se cancela inventario vendido por una edición de catálogo. La publicación futura verifica configuración disponible; dentro del proceso usa una llamada directa de aplicación. No se simula HTTP interno.

### Transacción de compra
1. Validar cliente, evento publicado, moneda y precios desde datos del servidor, nunca desde totales recibidos.
2. Reservar la clave `(customer_id, operation, idempotency_key)` con restricción única y hash del payload canónico. Canonizar ordenando los items por zona/asiento y consolidando cantidades de zonas generales. Duplicar el mismo asiento en un payload es 422. Claves de 1–128 caracteres, persistidas con la orden sin expiración automática en esta etapa.
3. Bloquear filas de inventario en un orden estable de IDs con `SELECT ... FOR UPDATE`. Para cupo general, decrementar con condición `available >= quantity`; para asiento, ocupar su fila solo si estaba disponible. Restricciones `CHECK` mantienen `0 <= available <= capacity`. Un asiento tiene una única fila de estado, no una asignación activa por cada reintento.
4. Si falta cualquier item, rollback completo. Si todos están disponibles, crear Order/OrderItems/Tickets, persistir resultado de idempotencia y commit conjunto.
5. Una colisión concurrente de clave espera la transacción original y relee el resultado después de rollback de su intento. Mismo hash: devolver orden existente; hash diferente: 409. Los errores sin commit no consumen la clave y pueden reintentarse.

La respuesta inicial y el replay son 201 con el mismo ID de orden; replay agrega `Idempotency-Replayed: true`. Conflicto de inventario: 409. Timeout/deadlock: rollback, respuesta transitoria 503 y retry acotado del cliente con la misma clave. No reintentar infinitamente dentro de la transacción.

### Devolución — Etapa III
El cliente propietario crea una solicitud Refund pending, única por ticket en esta propuesta inicial. Verificar elegibilidad y propiedad; repetir devuelve la misma solicitud. Solicitar no invalida el ticket ni libera inventario. Solo el administrador puede aprobar o rechazar, registrando su ID, fecha y motivo de rechazo.

Para aprobar: bloquear inventario por ID y luego ticket y solicitud por ID, en orden estable compartido con otras operaciones. Releer el estado de la solicitud bajo lock. Si ya está approved, retornar la misma decisión sin reponer de nuevo; si está rejected, responder 409. Si está pending y cumple elegibilidad, en un commit cambiar Refund a approved, Ticket a refunded, actualizar Order y liberar exactamente un lugar. Si falla cualquier escritura, rollback completo.

Para rechazar: bloquear la solicitud y cambiar pending a rejected, con motivo no vacío y auditoría. No tocar ticket, orden ni inventario. Repetir rechazo devuelve la decisión previa; intentar rechazar una solicitud approved devuelve 409. En una carrera aprobación/rechazo gana una única transición terminal; nunca se aplican ambas. La implementación futura debe probar estas carreras con PostgreSQL.

Propuesta inicial de fechas: solicitud y aprobación antes del inicio del evento; rechazo permitido después para resolver pendientes. Reapertura tras rechazo y cualquier cambio de esta política se acordarán antes de implementar. Una compra nueva del asiento liberado genera otro ticket; el anterior sigue inválido. Pasarela y devolución monetaria real fuera de alcance.

### Comunicación futura
HTTP síncrono para consultas que requieren respuesta inmediata; eventos asíncronos `OrderConfirmed` y `TicketRefunded` para efectos secundarios. Al extraer servicios, outbox en el mismo commit que la compra, entrega al menos una vez y consumidor idempotente por `event_id`; versión de esquema explícita. No se incorpora broker ni worker ahora. Una caída de notificaciones jamás revierte una compra confirmada. La extracción de Identity deberá definir validación de sesiones y disponibilidad en otro ADR; este documento no promete llamadas distribuidas atómicas.

## Alternativas y consecuencias
Separar cada entidad daría autonomía, pero requeriría sagas y compensaciones prematuras. Una transacción única facilita demostrar consistencia y permite pruebas reales en PostgreSQL. El costo es acoplamiento de despliegue inicialmente, aceptado explícitamente. Los módulos se comunican mediante funciones de aplicación, sin escrituras directas a tablas ajenas. Política de reservas, pagos y cancelaciones masivas pendiente de un nuevo change.
