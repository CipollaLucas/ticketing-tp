# ADR-0003 — Identidad y sesiones revocables

Fecha: 2026-11-23. Estado: diseño aprobado por el usuario para implementar; pendiente de revisión cruzada del PR. Issue #6, change authentication-and-roles.

## Contexto y alternativas
La API FastAPI/PostgreSQL necesita identidad y permisos antes de habilitar eventos y compras. JWT agregaría firma, claims y revocación; cookies de sesión requerirían acordar CSRF y cookies entre frontend/API. Se elige Bearer opaco con sesiones persistidas porque permite revocación sencilla y una implementación pequeña en el stack existente.

## Decisión
- User con UUID, username ASCII normalizado único, display_name, hash Argon2 y rol restringido por CHECK.
- Única dependencia nueva: `pwdlib[argon2]>=0.3,<1`, siguiendo [la documentación de FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/), para no implementar hashing propio. No se incorpora JWT ni framework de usuarios.
- Token aleatorio de 32 bytes codificado URL-safe; solo hash SHA-256 en AuthSession. Consulta de sesión y usuario por request, expiración UTC y borrado al salir. Duración configurable de 60 a 86400 segundos, default 3600.
- Registrar crea solo customer; payloads extra se rechazan. CLI local crea administradores sin password por argumentos ni credenciales predefinidas.
- Guards separados para rol administrador, rol organizador/admin y propiedad/admin. La propiedad proviene de datos del servidor; no de owner_id recibido.
- PATCH de perfil únicamente display_name. Cambio de roles solo admin; no permite modificar el propio rol. Rol leído en cada request sin cache en token.
- Login tiene error genérico y verificación ficticia de hash si no existe el usuario. Errores de validación conservan detail/loc/msg/type pero omiten input para no devolver passwords. Logs HTTP no incluyen body ni Authorization.
- Cambios de rol serializados bloqueando administradores por UUID en orden estable; verificar nuevamente el rol vigente después de esperar el lock, para impedir degradación mutua concurrente.
- CI usa PostgreSQL 16 temporal únicamente para tests de migración/concurrencia; no agrega infraestructura productiva.
- Migraciones explícitas con Alembic, sin create_all al iniciar la aplicación.

## Consecuencias y límites
Cada request protegido consulta la base; si la base falla, no se autentica usando un fallback inseguro. El frontend futuro debe mantener token en memoria, descartarlo en logout/401 y usar HTTPS fuera de localhost. No hay refresh, recuperación de contraseña, email, MFA ni límites de intentos de acceso en este incremento local. Antes de exponer un login a Internet se debe definir protección contra abuso, operación TLS y gestión de sesiones expiradas; no se incorpora infraestructura nueva en este change.

El guard de eventos se verifica con una ruta exclusiva del test; la API productiva todavía no implementa CRUD de eventos. La documentación no declara que validar SQLite pruebe concurrencia PostgreSQL. [Plan de implementación](../openspec/changes/authentication-and-roles/tasks.md).
